# Issue-selection rubric

This rubric is used by the `issue-select` skill to score candidate Path Review issues.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Repo active | repo-facts block: default-branch commits, last push, latest release, archived flag | Pass if the repo is not archived and its last default-branch push or its latest release falls within roughly the last 6 months before the capture date. Compute the actual gap between the capture date and the last push/release rather than eyeballing it; a repo with high stars or many open issues but no push or release in the last 6+ months still fails this check | required |
| Bounded work | issue body and comments | Pass if the issue is a single concrete bug, doc task, or small feature with a local edit surface and a reasonably clear patch area; fail umbrella issues, codebase-wide sweeps, tracking-list megaissues, broad redesigns, and issues with a long history of unresolved design debate or a still-uncertain scope. A bug with several plausible root causes, or several concrete implementation approaches (e.g. multi-threading, multi-processing, caching, narrowing what gets processed), still passes as long as all of them target the same narrow user-facing symptom and the same subsystem — count subsystems touched, not bullet points listed; a maintainer bundling multiple named causes or fix ideas for one freeze/slowdown/crash is still one bounded bug. Optional follow-on suggestions listed alongside the core fix (e.g. "we could also...", ideas for later) do not expand the required scope as long as the core fix is what the issue actually asks for. A docs task passes when it identifies a specific permanent docs home (even a new page to create) plus a small, named set of existing pages to update — it does not need to be a single-file edit. Treat multiple closed or abandoned linked PRs spanning years, combined with hedging or unresolved language ("perhaps", "discussed here" with no settled conclusion), as evidence of a long-running design debate that fails this check even when no PR is currently open | required |
| Specific expected behavior | issue body and comments | Pass if the issue explains the user-visible symptom, the desired behavior, or the concrete output expected from the change; documentation tasks count when they name the target page(s) or a permanent docs home and the update is concrete. A task does not need a formal reproduction script or exact code diff to count, but it must clearly state the intended outcome. A very short, maintainer-filed bug report still passes when it names several specific, checkable items (feature names, rule names, function names) even in a one-line comma list ending in "etc." — a trailing "etc." on an otherwise concrete named list is not itself vague, since the named items already give a patch author somewhere to start. Vague proposals or large feature wish lists with no named specifics fail | required |
| Unclaimed and available | issue metadata, comments, linked PRs, assignees | Pass if there is no assignee, no linked open PR, and no active claim comment suggesting someone is already working on it. Judge "active" by recency: a claim comment ("I'd like to work on this", "@bot claim") from months or years before the capture date, with no follow-up activity afterward, is a stale claim, not an active one — this is especially clear when a stale-bot comment later marked the issue inactive or a maintainer later bumped/re-invited contributors. Treat only a claim comment with recent, ongoing follow-up (or a currently open linked PR, or a currently set assignee) as blocking | required |
| Policy compatible | repo-facts policy line | Pass only if the repository does not explicitly forbid AI-generated code or documentation, or any other contribution workflow being used for this task. Reject if the repo's contributing docs say not to use AI-generated code or docs | required |
| Good first issue signal | issue labels and comments | Pass if the issue is tagged `good first issue` or otherwise clearly described as a small local fix by a maintainer; use to rank accepted issues, not to block a valid first contribution | preferred |

## Verdict rule

Accept only if all required checks pass. `reject` if any required check fails. Preferred checks never change the verdict; they only help rank accepted issues. If the needed evidence is missing, treat it as a fail instead of guessing.

Notes
- This rubric still rejects dead repos, claimed work, policy blockers, and broad design issues, but it does not require a label to treat a narrow bug or doc task as a valid first contribution.
- A small doc task or a maintainer-filed bug remains a valid first issue even when it is not explicitly tagged `good first issue`.
